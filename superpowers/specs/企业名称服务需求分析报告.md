## 1. 基础约束与数据有效性

📄 **来源：[准C逻辑] §1.1、§1.2；[Demo设计] 系统逻辑章节；[会议记录] 核心原则部分**

### 1.1 基础逻辑约束

| 编号 | 规则 | 来源 |
|------|------|------|
| B-01 | 同一时间，一个有效企业名称有且仅有一个当前有效企业 | [准C逻辑] §1.1-1；[Demo设计] |
| B-02 | 同一时间，一个企业仅有一个权力人有效 | [准C逻辑] §1.1-2；[Demo设计] |
| B-03 | 统一社会信用代码与企业 UUID 唯一绑定，永不合并 | [准C逻辑] §1.1-3；[会议记录] 三层ID体系 |
| B-04 | 公域使用 UUIDv4.0 随机模式；内部排序使用自增 ID，禁止插队 | [准C逻辑] §1.1-4；[会议记录] 三层ID体系 |
| B-05 | 企业预置位置信息先天存在，永远不变 | [准C逻辑] §1.1-5；§1.4-2 |
| B-06 | 新增企业信息必须通过拉新服务写入，保障逻辑连续性 | [准C逻辑] §1.1-6 |
| B-07 | 事实数据表/库不直接面对服务对象 | [准C逻辑] §1.6-4；[Demo设计] |
| B-08 | 全量事实数据永久存在，按逻辑需要供给业务 | [准C逻辑] §1.6-7；[Demo设计] |
| B-09 | 数据变化触发业务，调度机制基于 Dapr | [准C逻辑] §1.6-5；[Demo设计] |

## 2. 企业名称-数据更新模块

### 2.1 拉新总体架构

📄 **来源：[流程图] 整体架构图；[准C逻辑] §1.3；[会议记录] 任务单机制**

**拉新场景分类**

```
数据来源
├── 批量低频  → 基础拉新（初始基础数据池）
├── 用户触发  → 用户拉新（天眼查截图）
├── 业务触发  → 业务拉新（企业信息列表）
└── 企业自主  → 公司拉新（企业信息说明）
                       ↓（统一）
               生成任务单（任务单机制）
                       ↓
               逐条执行相同生产逻辑
```

**任务单内容**（📄 来源：[会议记录]）：采信来源、凭证、处理规则、结果

> ❓ **缺口 G-02**：任务单机制在[会议记录]中明确提出，但在[准C逻辑]和[Demo设计]中均无对应的数据结构定义和状态流转说明（如：排队、处理中、成功、失败）。

### 2.2 基础拉新（批量初始化）

📄 **来源：[准C逻辑] §1.3-1；[流程图] 批量拉新分支；[Demo设计] 基础数据池入巢；[会议记录] 批量拉新成本考量**

#### 2.2.1 数据来源与输入形式

| 输入形式 | 说明 | 来源 |
|---------|------|------|
| 结构化文件（.sql/.csv/.xls/.json 等） | 企业工商数据文件 | [流程图] 文件拦截服务/企业名称文件目录 |
| 图片文件（.png 等） | 需经 OCR 识别 | [流程图] 图片识别分支 |
| 数据要素 | 企业名称、统一社会信用代码、权力人名称 | [Demo设计] 基础数据池章节 |

> ⚠️ **矛盾 C-02**：[流程图]中批量拉新的数据准备包含"一批企业名称信息的文件"和"企业信息截图"两种形式，且截图路径需经过 OCR 识别并进入"图片文字识别库"；但[准C逻辑]§1.3-1 的"基础拉新"步骤 a 仅写"获取基础数据"，未提及截图或 OCR，与流程图存在信息不对称。

#### 2.2.2 处理流程

```
原始数据文件
  ↓ 文件解析（.sql/.csv/.xls/.json/.png）
  ↓（图片路径）图片 OCR → 提取三要素
  ↓
数据完整性校验
  ├── 通过 → 生成任务单入队
  └── 失败 → 记录失败日志，跳过当条
  ↓
任务单逐条处理
  ↓
企业有效性校验（V-02 ～ V-07）
  ├── 失败 → 记录失败日志
  └── 通过 → 进入去重处理
  ↓
去重处理（详见 §2.7）
  ↓
入巢（写入 PostgreSQL 事实数据）
  ↓
全量入巢验证：写入后信息 = 写入前信息
  ↓
触发 ES 索引同步（Dapr 事件驱动）
```

📄 处理流程来源：[准C逻辑] §1.3-1；[流程图] 批量拉新分支；[Demo设计] 入巢处理流程

#### 2.2.3 同名不同企的成本策略

📄 **来源：[会议记录] 批量拉新成本考量**

- 若外部验证（天眼查等）**成本可控**：拉新获取最新数据
- 若**成本过高**：随机选一个作为初始值，后续靠用户申诉修正，该条不生成独立任务单

> ⚠️ **矛盾 C-03（关键矛盾）**：本条策略与[准C逻辑]§1.3-1.c "同名不同企，随机留一个"部分一致，但与[会议记录]核心规则"所有同名企业都存入，不合并，每个企业独立存在"**直接矛盾**。详见 §4 矛盾汇总。

### 2.3 用户拉新

📄 **来源：[准C逻辑] §1.3-2；[流程图] 单条拉新分支；[Demo设计] 企业名称申诉章节**

#### 2.3.1 触发场景

用户搜索不到目标企业名称，主动上传天眼查截图申请新增。

#### 2.3.2 处理流程

```
用户提交天眼查截图
  ↓
OCR 识别（双 AI 模型比对）
  → 提取：信用代码、企业名称、权力人名称、企业地址        ← [准C逻辑] §1.3-2.b
  → 提取：信用代码、企业名称、权力人名称（仅三要素）      ← [Demo设计] 申诉流程
  ↓（⚠️ 两文档提取字段不一致，见矛盾 C-04）
天眼查"验实"：OCR 结果与第三方数据源一致性校验
  ↓
企业有效性校验（V-02 ～ V-07）
  ↓
企业地址 → 位置预置处理（§2.6）
  ↓
判断企业名称是否已存在
  ├── 不存在 → 入巢写入
  ├── 同企不同名 → 复用已有企业 UUID，挂载新名称版本
  └── 同名不同企 → 转交权力人采信服务处理（⚠️ 见缺口 G-03）
  ↓
首支验证（用户确认）
```

> ⚠️ **矛盾 C-04**：OCR 提取字段不一致。
> - [准C逻辑] §1.3-2.b：OCR 提取**四要素**（代码、企业名称、权力人、**企业地址**）
> - [Demo设计] 申诉/申诉步骤：OCR 提取**三要素**（代码、企业名称、权力人），无地址
> - 企业地址是否为 OCR 提取对象，两文档存在冲突。若不提取地址，位置预置信息无法在用户拉新中自动生成。

> ❓ **缺口 G-03**：[准C逻辑] §1.3-2.f 说"同名不同企（只存在于权力人申诉场景，放在权力人采信服务中实现）"，但"**权力人采信服务**"在所有文档中均**未定义**，其服务边界、处理逻辑、接口均无描述。

### 2.4 业务拉新

📄 **来源：[准C逻辑] §1.3-3**

#### 2.4.1 触发场景

业务系统提供企业信息列表（如万品通），批量新增企业数据。

#### 2.4.2 处理流程

```
获取业务数据（企业信息列表）
  ↓
企业信息处置：天眼查形式化验实 + 企业地址 → 预置位置信息
  ↓
企业有效性校验（V-02 ～ V-07）
  ↓
判断是否已存在
  ├── 同企不同名 → 复用已有企业 UUID
  └── 同名不同企
        ├── 原企业有权力人主张
        │     ├── 原企业仍正常经营 → 不允许拉新
        │     └── 原企业不在正常经营 → 拉新成功，标注原企业不在经营
        └── 原企业无权力人主张 → 允许拉新（⚠️ 见缺口 G-04）
  ↓
入巢 + 首支验证（由业务方确认）
```

> ❓ **缺口 G-04**：[准C逻辑] §1.3-3.e 仅描述了"原企业有权力人主张"的两种子情况，**未明确"原企业无权力人主张"时业务拉新的处理路径**。从逻辑推断应允许拉新，但文档无明确说明。

> ❓ **缺口 G-05**："判断是否还正常经营"——所有文档均未说明通过何种机制判断企业经营状态（是否调用天眼查 API？判断标准是什么？超时如何处理？）。

### 2.6 企业位置预置服务

📄 **来源：[准C逻辑] §1.4；[会议记录] 位置数据的独立性与关联**

#### 2.6.1 核心规则

- 每个企业的预置位置信息先天存在，永远不变（📄 [准C逻辑] §1.4-2）
- 位置本体应作为独立数巢服务维护，企业名称服务中"预置位置"仅为引用（📄 [会议记录]）

> ⚠️ **矛盾 C-06（架构层面）**：
> - [准C逻辑] §1.4 将位置预置服务作为企业名称服务的子流程，描述了完整的处理逻辑
> - [会议记录] 明确提出"位置需要独立的数巢服务，企业名称服务中的预置位置只是引用"
> - 两文档对位置服务的**归属**（独立服务 vs. 子流程）定义相反，是架构级矛盾，需决策。

#### 2.6.2 位置准确率处理机制

📄 **来源：[准C逻辑] §1.4-3**

| 场景 | 处理方式 |
|------|---------|
| 代码解析省编码 = 腾讯地图返回省编码 | 对腾讯地图返回信息处理后直接使用 |
| 省编码不一致 + 地址含省/自治区/直辖市信息 | 对腾讯地图返回信息处理后直接使用 |
| 省编码不一致 + 地址不含省级信息 | 用代码解析的省市县补充地址后，再调用腾讯地图 |
| 其他特殊情况 | 补省后默认使用省人民政府地址，再调用腾讯地图 |

#### 2.6.3 位置三要素转化流程

📄 **来源：[准C逻辑] §1.4-4**

```
企业地址
  ↓
[Step 1] 调用腾讯地图「地址解析 API」
  → 按准确率机制 → 得到地理坐标
  ↓
[Step 2] 调用腾讯地图「逆地址解析 API」（输入：地理坐标）
  → 按距离优先级选取第一个不含括号的 POI
  → 以该 POI 三要素作为企业位置三要素
  ↓
[特殊路径] 地址最终落到省人民政府时
  → 调用腾讯地图「关键词搜索 API」直接获取位置三要素
  → 跳过地址解析流程
```

> ❓ **缺口 G-07**：[准C逻辑] §1.4 说"企业预置位置信息先天都存在，永远不变"，但[Demo设计]描述的**基础数据池仅含三要素（企业名称、信用代码、权力人名称），无企业地址字段**。若初始数据无地址，则无法通过位置三要素转化流程生成位置信息，"先天存在"的前提不成立。**初始化阶段如何处理无地址数据，所有文档均未定义。**

> ❓ **缺口 G-08**：腾讯地图 API 调用的错误处理未定义（接口超时、地址无法解析、POI 返回为空时的降级策略）。

#### 2.6.4 地标与地址的区别

📄 **来源：[会议记录]**

#### 3.1.2 输入规则

📄 **来源：[搜索产品] 总体规则-输入部分**

**支持的输入内容**
- 企业现用名称的汉字
- 企业现用名称的拼音

**不支持作为检索词**
- 公司英文名称、法人姓名、企业电话、企业信用代码、企业曾用名

**触发检索最低条件**：`包含 1 个独立有效关键词` 且 `总汉字数统计值 > 2`

> ❓ **缺口 G-14**：触发条件中"总汉字数的统计值大于2"对**混合输入（汉字+拼音）**的计算方式未定义。拼音部分是否计入汉字数？如何计入（以拼出的汉字数计还是字母数计）？文档无明确说明。

**独立有效关键词定义**

| 输入类型 | 成为独立有效关键词的条件 |
|---------|------------------------|
| 纯汉字 | 至少包含 1 个汉字（特定词除外） |
| 纯拼音 | 至少能完整拼出 3 个汉字 |
| 汉字+拼音混合 | 拼音部分能拼出至少 1 个完整汉字 |

**非独立有效关键词（需与其他词组合）**

| 类别 | 示例 |
|------|------|
| 省市区县名称及简称 | 宁夏、海淀、广东、深圳 |
| 公司类型名称及相关词 | 有限、责任、公司、有限责任、有限公司、有限责任公司 等 |

**关键词分隔与检索触发规则**

- 关键词以空格分隔，每个关键词检索时作为整体，不拆分、不截断
- 每多输入一次有效字词，触发一次检索
- 非独立有效关键词与其他独立关键词组合时，整体作为一个有效关键词
- 不支持：拼音中间含空格；一个关键词内含两部分拼音

#### 3.1.3 输出规则

📄 **来源：[搜索产品] 总体规则-输出部分**

| 规则 | 说明 |
|------|------|
| 名称完整显示 | 企业名称在列表中完整展示 |
| 关键词高亮 | 匹配的关键词在列表中高亮显示 |
| 权力人显示 | 最多显示 5 个字；是否显示可通过 API 入参控制 |
| 汉字模糊 | 不提供相近字模糊检索 |
| 拼音同音 | 拼音需检索出全部同音字 |
| 完整性 | 结果必须包含全部、完整的关键词（不限顺序，可相邻、重叠、重复） |
| 列表长度 | 固定；结果少时下方空白；结果多时出现滚动条；无结果时提示可申请新增 |
| 排序一致性 | 每个用户每次使用相同关键词检索结果排序具有一致性 |

#### 3.1.4 详细场景规则

📄 **来源：[搜索产品] 详细规则示例**

| 输入场景 | 输出行为 |
|---------|---------|
| 完整且正确的企业名称 | 列表中出现唯一一个备选企业 |
| 完整但有错别字 | 不提供相近字，按输入内容检索 |
| "广东" + "深圳"（空格分隔，各为省市简称） | 不触发检索，不做任何提示 |
| "广东深圳"（连写） | 视为独立有效关键词，触发检索，返回含"广东深圳"企业 |

| xianhuakan + "昆明" | "昆明"为第二关键词，组合检索 |
| 昆明 xianhuakan 商贸 | "昆明"第一、拼音第二、"商贸"第三，组合检索 |
| 昆明 xianhua 商贸 kan | 不支持（一个关键词内含两部分拼音） |

> ❓ **缺口 G-19**：两个数据源查询结果不一致时的处理策略未定义。

#### 3.6.3 五要素认证

| 项目 | 说明 |
|------|------|
| 输入 | 企业名称、统一社会信用代码、权力人名称、手机号、身份证号 |
| 输出 | 要素一致性结果 |

> ❓ **缺口 G-20**：五要素认证的实现方式（调用哪个第三方 API？超时处理？）在所有文档中均未定义。
